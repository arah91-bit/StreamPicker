# Public setup review: baseline ece395087

Scope: ticket #3 against the fixed public baseline `ece39508703780632ae1f24ad007ce633f0c5997` and parent #1. This is a static review of the committed public tree, not a clean-install, provider, upgrade, or player run. Severity expresses impact on the requested first-run journey; dispositions are proposals for subsequent tickets, not claims of completed fixes.

| ID | Severity | Finding and evidence at the baseline | Disposition |
| --- | --- | --- | --- |
| B1 | High | The wizard and Settings restart handlers discard every error from `POST /api/settings/restart` (`app/wizard.py`, `_JS`, and `app/settings_ui.py`, `doRestart`). The server explicitly returns 409 with the validation reason when pending configuration is invalid (`app/main.py`, `settings_restart`). Since the process remains healthy, the subsequent health poll can redirect or reload and suggest success even though no restart occurred. Both handlers also leave restart controls disabled on timeout. | Fix both flows to distinguish a rejected request from an accepted restart, show the reason and a retry/recovery action, and verify the new process has applied the settings before reporting success. Exercise rejection and timeout in browser-level tests. |
| B2 | High | The agent guide says both config surfaces take effect on restart and recommends `docker compose restart` or `up -d` after edits (`AGENTS.md`, model and “Then: restart”); `SETUP.md` troubleshooting makes the same blanket claim. Compose injects `.env` via `env_file` and interpolation (`docker-compose.yml`), so restarting an existing container does not replace its environment. An agent changing `.env` can believe stale values were applied. Dashboard `config.json` writes are mounted separately. | Correct the guides to distinguish restarting for mounted config changes from `docker compose up -d` recreation after environment changes; verify the effective values after each path using a clean Compose run. |
| B3 | Medium | The wizard displays provider failure details and allows another attempt (`app/wizard.py`, `showChecks` and click handler), but when a single working source accompanies a failed one it advances directly to a restart-only phase and says failed items “can wait.” There is no visible way in that phase to correct and retest the failed item without leaving/reloading. With no source, it offers only a generic “add ... then try again” message in addition to raw check details. | Preserve a clear edit/retry path after partial failure and give actionable service-specific guidance without exposing credentials. Cover failed source then successful retry and partial success. |
| B4 | Medium | Save errors are surfaced (`app/settings_ui.py`, `doSave`; `app/wizard.py`, click handler), and `config.save` validates before writing (`app/config.py`, `save`). However neither setup documentation nor the UI explains how to recover from a persistent write/validation failure, distinguish unsaved changes from saved pending changes, or check container storage/logs. The wizard's API can return a generic error for non-validation failures. | Add specific recovery guidance and maintain entered values on failure; cover rejected validation and storage failure without logging credentials. |
| B5 | Medium | The update instructions preserve `.env` and `./data` but omit the separately mounted encryption key (`README.md`, “Updating”; `docker-compose.yml`, volumes). The guide does explain separately that a different key cannot decrypt saved passwords (`SETUP.md`, troubleshooting), and encrypted-config tests cover wrong and missing keys (`tests/test_encrypted_config.py`). A move/restore that saves only the named files loses access to credentials. | Make the upgrade/backup instructions explicitly preserve the matching `secrets/stream-picker-config.key` with the data and verify an upgrade with the original key, saved settings, link, and stream. |
| B6 | Medium | The shipped CI builds an image and runs pytest with `docker run --entrypoint sh` (`.github/workflows/publish.yml`), bypassing the published Compose contract and normal entrypoint. Unit tests exist for enrollment, wizard, encryption, settings and proxies, but this does not establish fresh Compose startup, either setup-to-stream journey, media bytes, or preservation on upgrade. | Add reproducible clean-install and upgrade verification through published interfaces with a deterministic source; keep browser and agent states independent. Parent #1 records making these required release gates as an unconfirmed recommendation. |
| B7 | Medium | README provides manifest patterns and Setup explains LAN/player reachability (`README.md`, “Install in your player”; `SETUP.md`, steps 3–5 and troubleshooting), while `app/home_ui.py` exposes a copyable manifest. No baseline evidence establishes that a stock public Nuvio version accepts the link and plays returned media. Readiness (`app/main.py`, `/health/ready`) is not a stream or playback check. | Perform and record a stock public Nuvio version/platform/install/playback smoke test on the candidate; document readiness, source and playback checks separately. Do not infer client compatibility from route or unit-test existence. |
| B8 | Low | The human instructions give a prebuilt Compose path, enrollment, one-source options, address advice and troubleshooting (`README.md`, Quick start; `SETUP.md`, steps 1–5 and sections 4 and 8). `AGENTS.md` identifies the generated `.env.reference`, precedence, encrypted save, CSRF API and validation, but does not give a complete executable agent recipe from clean startup through independent readiness, stream and readable-media checks. | Add an unattended walkthrough using the existing interfaces, including user-supplied prerequisites, safe secret handling and verification evidence. Do not invent a new configuration surface. |

The wizard saves only successful checks and refuses to save if no stream source passed (`app/wizard.py`, `apply`); existing tests cover no working lane, one failed lane, and secret non-echo (`tests/test_setup_wizard.py`). These are useful foundations, but an addon manifest test or provider search result alone does not prove playback. Settings precedence and encryption are implemented in `app/config.py` and `app/secret_store.py`; preserve those contracts when addressing the findings. No private integration, endpoints, or credentials are needed for these fixes.
